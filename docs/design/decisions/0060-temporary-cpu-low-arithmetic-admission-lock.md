# ADR 0060: Temporary CPU low-arithmetic admission lock

## Status

Accepted design under the user's first-production authorization, after independent scope and
source/seam review. Root and the owning backend contract coordinate the CPU-only cutover before
CPU0078 Ready. Implementation and numerical/consumer acceptance are recorded by
[CPU0078](../../planning/backends/cpu/tasks/0078-temporary-low-arithmetic-lock.md#result), not inferred
from this decision. The [reviewed matrix](../../backend-guide/production-support.md) remains the
release target/evidence ledger.

## Context

The user explicitly chose to retain, not expand and temporarily lock Java CPU BFLOAT16/FLOAT16
computation, while requiring Metal production support. Storage dtype alone cannot decide arithmetic
permission: exact selection, comparisons, raw movement and explicit conversion remain useful to
F32/F64 networks, and an output can be promoted while still consuming a low numerical operand.
Current prepared/cache/fixed-recurrent entry points cannot rely only on a fresh provider query.

## Decision

Keep the implementation and Model numerical semantics. Introduce no profile, runtime opt-in,
policy object, hidden F32 fallback, alternate backend or new production type/package. Existing
opcode/lowering/IR owners hold one CPU-local availability distinction, outside execution loops.
The [owning CPU contract](../../architecture/contracts/backend-execution.md#cpu0078-temporary-low-arithmetic-lock)
defines exact preserved/numerical families and the bounded cold signatures.

Authenticate at source/direct lowering, preparation and retained finalization, before any cache
hit or class definition, and independently before direct fixed-recurrent construction. Check actual
represented realization plans as well as semantic units. Numeric virtual values and typed MATMUL
operands matter; a low boundary feeding an explicit F32 CAST does not prohibit later F32 arithmetic.

SUM-derived constant-write IR has lost its numerical provenance. Reject that low physical family
at retained/IR admission; original graph-literal initialization remains shared Prepare work and
stays available. Do not add provenance solely to rescue this temporary optimization.

Direct generated-byte definition receives the exact canonical IR in addition to specialization
and bytes. Migrate every internal caller, with no two-argument bypass. Policy rejection precedes
weak/persisted cache reuse and stays outside miss/regeneration catches. Verify-only class inspection
retains its separate non-executing purpose and current trusted-local-byte threat model.

## Preservation and compatibility

All shared types, storage/borrowing/export, original literals, raw exact movement, conversions,
BOOL/integral control and exact unary/predicate/extrema/ordering/winner semantics remain. Explicit
low-storage -> F32 compute -> final storage conversion stays valid, including Training-owned
F32-working master/candidate updates. This does not authorize implicit emulation of a low operation.

No emitter mathematics, low kernel or generic optimizer is deleted or repaired by this lock.
OpenBLAS already restricts computation to F32/F64; the integral-only partial-reduction IR retains
its existing exclusion of every floating dtype. Empty/inactive work cannot bypass admission.

Allowed generated bytes, entry ABI and identities remain unchanged. The definition method's
extra cold argument is internal source migration, not a generated/native ABI. No arbitrary global
schema bump is warranted; any demonstrated changed emitted fact requires its own selective review.
Current ledger v2 records actual new CPU answers; historical v1 and every Metal answer stay intact.
Unlocking needs an explicit later decision and requalification, not a property or retry.

## Verification boundary

Before the cutover, actual public BF16 and FP16 ADD and explicit F32/cast-back/exact-ABS controls
were observed. Authentic old ADD Class-Files were generated and defined by the old generator for
both dtypes; these support real stale-artifact rejection fixtures without a production bypass.
The first fixture commands' F16 import/projection mistakes remain failed evidence; corrected F16
parts were exercised separately rather than relabeling the commands PASS.

Acceptance must prove unsupported numerical roles at all entry points, old-cache rejection,
retained raw bits/signed-zero/subnormal/discrete results, storage/F32 workflows and unaffected
F32/F64 neural journeys. No source, operation count or ordinary JVM-only success is by itself
first-release or Metal production readiness.
