# Metal Backend Master Plan

## Goal and authority

Maintain truthful Metal capability, MPSGraph/custom routes, native storage and resources across
cold preparation and synchronous execution. This is an implementation map, not a contract.
[ARCHITECTURE.md](../../../../ARCHITECTURE.md) and the incorporated
[backend contract](../../../architecture/contracts/backend-execution.md#metal-backend) are authoritative.

Required scoped headings for new work are Concrete backend modules, Metal backend, Low-precision
capability evidence, Profile-free backend capability and identity, and the applicable Prepare/Run
lifecycle headings in [runtime-prepare-engine](../../../architecture/contracts/runtime-prepare-engine.md).
The [backend guide](../../../backend-guide/metal-backend.md) and native README explain implementation.

## Current behavior and boundaries

- Model has one profile-free numerical contract. Exact stored/discrete/cast/movement boundaries
  stay exact; floating qualification uses operation/dtype/domain-specific conformance, not a
  runtime numerical certificate or an implicit relaxed profile.
- Planning chooses Metal ownership. Metal chooses the fixed route during analysis, declares
  resources, and finalizes only after shared assignment; Runtime invokes that prepared choice.
- FLOAT32 uses qualified MPSGraph/custom routes. Every low-containing partition selects only
  `CUSTOM_PROGRAM`; low-valued operations use typed custom steps with FLOAT32 working values.
  No hidden BF16→F16 substitution or low generated/anchor fusion is allowed.
- A new FLOAT32 occurrence does not automatically enable BF16/F16. Query and qualify each dtype
  separately; frozen v1 is history and current v2 tracks actual representative provider answers.
- One integration owns one default-device context and queue. Native handles are exact-context
  scoped; execution waits for completion. No asynchronous API, automatic device discovery,
  general mutable output pool, or unreviewed route fallback is implied.
- Transfers preserve represented bits and the complete checked physical span in the existing
  seven-dtype, rank-0..16 positive-stride non-overlapping domain. Native ingress/decoders,
  source/package authentication, pre-write validation and ownership checks remain mandatory.
- Local/complete-plan tuning is bounded to the existing eligible singleton FLOAT32 NEG case and
  session reuse. It is not general Metal autotuning or persisted executable reuse.
- Backend production never depends on Engine or Training. CUDA and CPU vendor routes remain
  separate owners.

## Package map

`io.github.pho001.synaptik.backend.metal` contains the supported capability/configuration,
trace observer, lifecycle integration and retained tuning collaborations, with package-private
native, resource, binding and route implementations. Extraction into new packages is deferred
until a concrete seam warrants it; no generic registry, manager or service locator is planned.
