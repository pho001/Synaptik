# Task 0007A0: Generated Hot-Path Parity Correction

## Status

Complete

## Goal

Correct every performance defect measured by the completed local audit under
`/tmp/synaptik-bytecode-benchmark` before adding another CPU semantic family. For the audited
large dense heap-array cases, generated scalar pointwise, generated Vector API pointwise,
generated cumulative scan, and generated ordinary aggregate execution must reach measurable
near-parity with equivalent direct Java loops while preserving all current semantics and general
fallbacks.

This is one cohesive generated-hot-path correction. Pointwise loop shape, scan/aggregate body
generation, typed carrier access, and generated-artifact compatibility meet at the same
`CpuClassFileKernelGenerator` and `CpuKernelSpecialization` boundary. Splitting them would either
leave known bridge-only hot paths in a newly versioned schema or permit compatibility reuse across
materially different generated bytes.

The correction supersedes only the former performance implementation assumptions recorded by
completed CPU 0005A/0005B/0005C/0005I/0007/0007A. Their semantic capabilities, tests, completion
status, and historical evidence remain valid and unchanged.

## Scope

### Audit baseline and correction target

- Treat `/tmp/synaptik-bytecode-benchmark/audit-summary.md`, its source, raw three-fork results,
  summary/ratio tables, commands, and captured bytecode as the initial reproducible defect
  evidence. The audited 1,048,576-element medians were 3.63x direct for generated scalar FLOAT64
  ADD, 1.84x for generated Vector API ADD, 1.32x for generated scalar ADD -> GELU_EXACT -> MUL,
  31.91x for generated FLOAT64 full MIN, and 5.45x for generated FLOAT32 CUM_SUM.
- Preserve equivalent direct Java loops as the comparison baseline. Generated-class creation,
  definition, cold carrier/geometry binding, allocation, initialization, verification, and output
  observation remain outside the timed region.
- Correct production code from evidence. Do not add a runtime feedback loop, benchmark-selected
  mutation, hidden global tuning state, or a relaxed acceptance threshold chosen to preserve the
  current implementation.

### Dense heap-array pointwise loop form

- When cold preparation and binding prove that one dense heap-array pointwise invocation's
  `start`, `end`, initial addresses, final addresses, and every vector/scalar array access fit the
  Java array-index domain, emit a canonical `int` index/address loop shape for every participating
  dense heap-array boundary.
- Keep the public/internal generated entry's shape-polymorphic primitive `long start, long end`
  contract. Perform any required checked narrowing once before the generated hot loop; do not
  bake compatible concrete extents, addresses, or element counts into class identity unless the
  emitted bytes actually depend on a structural proof category.
- Retain the existing checked `long` address/state forms for `MemorySegment`, mixed carriers,
  non-dense access regimes, ranges not proved int-safe, and every other general case. An
  optimization proof failure selects the correct general form; it never rejects an otherwise
  supported occurrence.
- Emit dense scalar array loads/stores and loop increments without per-element `long` arithmetic
  or `l2i`. Preserve arbitrary legal `start`/`end` subranges, scalar and zero-element behavior,
  all currently supported pointwise data types/opcodes, fusion lengths, and scalar/parallel
  orchestration.

### Dense heap-array Vector API loop form

- For the same proved dense heap-array regime, compute exactly one scalar `int` vector bound before
  the vector loop, run complete preferred-species vectors to that bound, and execute one scalar
  tail from the vector bound to `end`.
- Do not recompute `end - index`, reload the preferred species for each input, or maintain
  redundant long logical/address availability state on every vector iteration when structural
  specialization has made those facts constant or equivalent.
- Preserve exact existing vector eligibility, typed species, operation formulas, scalar fallback,
  arbitrary subranges, scalar tails, and parallel-vector range ownership. The correction does not
  broaden vector capability or change route-selection policy merely because one benchmark is
  faster.
- Retain the existing general vector state machines for supported non-dense contiguous-run forms
  and `MemorySegment` carriers unless an equally proved simplification applies without weakening
  semantics or bounds safety.

### Generated cumulative-scan hot bodies

- Replace bridge-only scan delegation with generated, typed, kind-specialized hot loops for every
  currently supported `CUM_SUM`/`CUM_PROD` combination: FLOAT64, FLOAT32, BFLOAT16, INT32, INT64;
  inclusive/exclusive; forward/reverse; scalar/parallel-scalar orchestration; heap arrays,
  `MemorySegment`, and mixed boundaries; and every supported resolved input/output layout.
- Generate dense heap-array fast paths with typed array locals and int-safe addresses when cold
  proofs permit. Keep correct typed long-address `MemorySegment` and arbitrary-layout fallbacks.
- Remove per-element `DataType`, scan-kind, and carrier dispatch. Do not pass each element through
  raw-bit/type switches or `Object` carrier classification. Select arithmetic, identity, carrier
  instructions, direction, and inclusive/exclusive placement structurally before the hot loop.
- Decode non-axis slice coordinates at most once per slice. Avoid division/modulo entirely for
  dense rank-one and other structurally direct forms; retain only the coordinate work genuinely
  required by a general layout/rank. Allocate no object per slice or element.
- Preserve exact sequential typed accumulation: FLOAT32/FLOAT64 same-format arithmetic,
  BFLOAT16 round-after-each-operation, INT32/INT64 modular arithmetic, positive-zero/positive-one
  identities, all special values, and bitwise scalar/parallel parity. Generated bounds continue to
  denote complete independent slice ordinals; one slice is never split between workers.

### Generated ordinary aggregate hot bodies

- Replace bridge-only aggregate delegation with generated, typed, kind/form-specialized hot loops
  for every currently supported `MIN`/`MAX`/`ALL`/`ANY` type and exact `FULL`, `SINGLE_AXIS`, and
  `MULTI_AXIS` form, including empty multi-axis selection, both keep-dimensions modes where valid,
  heap arrays, `MemorySegment`, mixed boundaries, and every supported resolved layout.
- Generate dense heap-array fast paths with typed array locals and int-safe addresses when proved.
  A full dense reduction must use a direct linear typed fold without per-element coordinate
  remainder/division. Single-/multi-axis dense layouts must avoid coordinate arithmetic wherever
  structural axis/layout specialization provides direct nested or contiguous spans.
- Keep a correct generated typed general-layout fallback. Coordinate division/modulo may remain
  only where arbitrary rank/strides require it; per-element type, kind, form, and carrier dispatch
  may not remain.
- Preserve exact empty identities, canonical logical row-major selected-domain order,
  first-logical-NaN represented-bit selection, signed-zero extrema preference, signed integral
  order, canonical BOOL output, BOOL short-circuit observability, and bitwise scalar/parallel
  parity. Generated ranges continue to own complete output cells only; no domain is split or
  combined and no workspace is introduced.

### Cold specialization, compatibility, and lifecycle

- Represent every emitted-code choice through typed CPU-private structural facts. Include an
  int-index/address proof category and any family body/layout specialization fact in deterministic
  specialization, fingerprint, class-byte, artifact-envelope, and process-local reuse identity
  exactly when it changes bytes or compatibility.
- Advance `CpuGeneratorSchema` once if generated bytes or compatibility facts change; older
  envelopes become safe incompatible misses and no migration reader is added. Preserve optional
  persistence, strong prepared-artifact ownership, single-flight reuse, corruption rejection, and
  shape-polymorphic reuse across compatible extents.
- CPU analysis remains deterministic and measurement-free. Finalization realizes or reuses the
  already selected compatible artifact only after shared slot assignment. Runtime receives the
  same immutable prepared executable and direct cold-bound carriers; it performs no generation,
  specialization, cache selection, graph inspection, or benchmark-driven mutation.
- Preserve complete-span overlap validation, carrier accessibility/writeability/alignment/size
  checks, output injectivity, range rules, worker ownership, zero workspace for current scans and
  aggregates, and concurrent-run isolation.

### Tests and performance evidence

- Add focused semantic differential and regression coverage for every current scan/aggregate
  kind, type, form, mode, carrier pattern, dense/general layout class, empty/singleton case,
  special value, arbitrary legal range, and scalar/parallel parity. Independent reference tests
  must not call production scan/aggregate emitters.
- Add stable automated generated-bytecode shape tests. Dense heap-array scalar pointwise bytecode
  must exhibit int loop/address locals without per-element `l2i`; dense Vector API bytecode must
  exhibit one precomputed bound, one vector loop, and one scalar tail; scan/aggregate generated
  classes must contain their typed specialized hot work rather than a bridge-only call to generic
  `execute(Object,Object,long[],long,long)` helpers.
- Add stable allocation/dispatch assertions for the hot bodies: no per-element/per-cell/per-slice
  allocation, reflection, boxing, map/string dispatch, `DataType`/kind/carrier switch, generic
  `Object` carrier access, or runtime graph/route/cache lookup. Prefer bytecode/class-shape tests
  over fragile source-text checks.
- Rework the local audit harness into an isolated reproducible multi-fork parity probe under
  `/tmp/synaptik-bytecode-benchmark` or a fresh documented `/tmp` directory. Keep the complete
  harness source, exact compile/run/summarize commands, environment facts, generated bytecode,
  raw samples, summary, ratios, and checksums together. The probe is evidence, not an ordinary
  Gradle/JUnit timing test and not a production setting selector.
- Measure at least five fresh JVM forks, at least five warmup batches, and at least nine randomized
  measurement rounds per case, with adaptive batches of at least 25 ms, fixed heap, deterministic
  inputs, pre/post exact output verification, and an observed output sink outside timing. Record
  preferred Vector species and JVM/OS/architecture facts.
- The audited large dense cases are FLOAT64 ADD scalar, FLOAT64 ADD preferred-species Vector API,
  FLOAT64 ADD -> GELU_EXACT -> MUL scalar, FLOAT64 full MIN aggregate, and FLOAT32 inclusive
  forward CUM_SUM scan, each at 1,048,576 elements and compared with an equivalent direct Java
  loop using the same operation helper/formula where applicable.
- Near-parity acceptance is per case: the median of generated per-fork medians must be no more than
  `1.15x` the median of the corresponding direct-loop per-fork medians. Fifteen percent is a
  reasoned tolerance: it is materially tighter than the measured 1.32x-31.91x defects while still
  exceeding the audit's maximum 3.55% cross-fork coefficient of variation enough to absorb local
  microbenchmark and scheduler noise. Report every fork and ratio; do not average failing cases
  together or widen the threshold after seeing results.
- If any audited large dense case exceeds `1.15x`, keep the task `In progress` or `Review needed`,
  investigate code shape/JIT evidence, and correct the implementation. Environmental invalidity
  may justify rerunning the unchanged protocol; it does not justify marking the performance
  objective complete. Timing is never added to the ordinary unit-test gate.

## Architecture constraints

- Planning continues to select CPU ownership only. CPU analysis owns deterministic lowering,
  structural specialization, route/strategy selection, and exact declarations; CPU finalization
  owns compatible generation/reuse after shared assignment; Runtime executes the immutable result.
- Generated hot code sees direct typed carriers and primitive cold geometry. It must not see
  `Operation`, `CompiledNode`, graph objects, backend discovery, route choice, cache policy, or
  benchmark evidence.
- Prepared recipes remain immutable and reusable. Concurrent runs retain distinct `RunState` and
  invocation-private coordinate state; generated classes retain no mutable run state.
- Shape-polymorphic `start`/`end` entries, exact current semantics, all supported layouts/carriers,
  complete cold validation, resource declarations, and cache lifecycle remain unchanged.
- Performance evidence is observational and report-oriented. It neither selects nor mutates a
  production setting. Runtime tuning and benchmark-driven mutation remain forbidden.
- Work stays inside `backends/cpu` plus its existing CPU documentation/planning records. Stop if
  parity requires a shared contract, public API, dependency, architecture, Model semantic, new
  resource, or route-selection change.

- Use a cold-proved int-index/address code-shape category while retaining the universal long entry
  and all general long forms. This targets measured heap-array overhead without narrowing the
  supported carrier/layout/range domain.
- Require generated typed scan/aggregate bodies rather than optimizing the generic bridge helper.
  Structural specialization already knows kind, type, form/mode, access plan, and carrier pattern;
  retaining their per-element dispatch would contradict the CPU hot-path contract and the audit.
- Set the large-case gate to `1.15x` per case. The audit's worst cross-fork coefficient of
  variation was 3.55%; 15% provides substantial environmental allowance while remaining a real
  near-parity objective.
- Keep the timing harness isolated from ordinary tests and production selection. Stable semantic
  and bytecode-shape invariants belong in automated tests; noisy wall-clock evidence belongs in a
  reproducible multi-fork report.

## Known limitations

- The required timing gate applies to the five audited large dense heap-array cases on the local
  validation environment. It is not a universal hardware or workload speedup claim.
- MemorySegment and arbitrary-layout fallbacks require semantic and bytecode/allocation evidence
  but are not assigned a timing threshold by this audit because they were not measured initially.
- The task does not require machine-code disassembly or attribute a remaining effect to JIT
  inlining, auto-vectorization, or bounds-check elimination without evidence.
- Small-array call overhead may remain distinguishable from an inlined direct loop, but no
  bridge-only scan/aggregate implementation or avoidable dense-loop defect may remain.
