# Task 0007A0A: Affine and Movement Generated-Loop Parity

## Status

Complete

## Goal

Establish direct-loop performance parity for the remaining generated families that already embed
typed work in their generated class: affine boundary copies and non-affine represented-bit data
movement. Optimize only cold-proved dense heap-array forms while preserving the universal
shape-polymorphic `long start, long end` entry contract, every current carrier/layout form, and the
completed semantics of CPU 0006, 0006A, 0006A1, and 0006B.

This is the immediate first slice of the post-0007A0 corrective sequence. It shares one correction
boundary because `CpuAffineCopyEmitter` and `CpuDataMovementEmitter` already emit typed carrier
loads/stores and primitive loops; both still retain avoidable long logical/address state and array
index conversion in cold-proved dense heap-array cases. It does not include any bridge-only family.

## Scope

### Reproducible baseline

- Before changing production code, create an isolated `/tmp` probe that measures the current
  generated class against an equivalent direct Java loop for each required case below. Retain
  source, exact compile/run/summarize commands, environment facts, generated bytecode, raw fork
  samples, summaries, ratios, and checksums together.
- Time only warmed generated-entry execution and the equivalent direct loop. Exclude lowering,
  generation, class definition, cold binding, allocation, input initialization, and result
  verification from the timed region.
- Required large dense heap-array cases, each with at least 1,048,576 output elements:
  - FLOAT64 affine `CONTIGUOUS` boundary copy with identity source/result addresses;
  - FLOAT32 `TILE` with a dense input and a repeated final axis; and
  - INT32 `SLICE_UPDATE` with a dense base, dense update, and a non-empty interior replacement.
- Use equivalent direct loops with the same mapping and represented-bit behavior. Do not compare a
  generated general-layout algorithm with a semantically different library bulk-copy operation.

### Cold-proved dense heap-array forms

- Reuse CPU 0007A0's typed `DENSE_HEAP_ARRAY_INT` proof category when its existing facts are
  sufficient. Extend typed CPU-private specialization only if affine/movement compatibility needs
  an additional byte-changing structural distinction.
- Keep generated entry parameters shape-polymorphic and long-typed. Narrow `start`, `end`, initial
  addresses, and other proved array-index facts once before the hot loop. A failed proof selects
  the existing correct general-long form; it never rejects a supported occurrence.
- For dense affine copies, emit integer logical/address locals and direct primitive-array loads and
  stores without per-element long multiply, long-to-int conversion, or geometry-table address-pair
  decoding when the cold proof makes the source and result progressions affine and unit-stride.
- Preserve the existing address-pair/general form for non-unit, arbitrary-layout, segment, mixed,
  or otherwise unproved affine copies.
- For each current movement family (`PAD`, `TILE`, `CONCAT`, `STACK`, `UNFOLD_AXIS`, `UNFOLD2D`,
  and `SLICE_UPDATE`), specialize dense heap-array output traversal to integer logical/address
  state when cold facts prove it safe. Hoist invariant geometry loads and family choices outside
  the element loop where the emitted structural form makes them invariant.
- Preserve the family-specific generated mapping. Do not replace canonical mapping with a bulk
  copy, vector route, or different traversal unless represented-bit semantics, arbitrary legal
  ranges, and exact output ownership remain identical.
- Keep typed `long` address/geometry fallbacks for `MemorySegment`, mixed carriers, arbitrary
  layouts, non-unit/zero strides, large ranges, and every form not proved int-safe.

### Generated-code and lifecycle invariants

- Generated dense hot loops contain no per-element carrier/type/family switch, allocation,
  reflection, boxing, map/string dispatch, runtime graph inspection, route lookup, or cache lookup.
- Preserve current scalar and parallel-scalar range ownership, zero/scalar domains, represented-bit
  copying for all six current data types, typed padding bits, input deduplication, output
  injectivity, overlap rejection, accessibility/writability checks, and invocation-private geometry.
- Keep CPU analysis deterministic and measurement-free. Performance evidence is observational and
  must not alter ordinary preparation or Runtime behavior.
- Advance `CpuGeneratorSchema` only if serialized generated bytes or compatibility facts change.
  If it advances, reject the prior schema as an incompatible miss without a migration reader and
  update all exact schema assertions. If bytes and compatibility do not change, record why no bump
  is correct.

### Stable tests and parity gate

- Add generated-bytecode/class-shape assertions that prove dense affine and each structurally
  representative movement body contain their typed hot loop rather than a helper bridge, use the
  intended integer loop/address form, and contain no per-element `l2i` or repeated invariant
  geometry decode. Keep general-long fallback shape assertions.
- Prefer parsing Class-File instructions/constant-pool references through a reusable test helper
  over source-text matching or fragile absolute bytecode offsets. A recurring invariant belongs in
  automated tests rather than a manual `javap` ritual.
- Add semantic differential coverage for dense optimized and general fallback forms across every
  current movement family, represented type, heap/segment/mixed carrier class, arbitrary legal
  range, scalar/zero case, and scalar/parallel parity. Independent expected results must not call
  the production emitter.
- The isolated probe uses at least five fresh JVM forks, five warmup batches, and nine randomized
  measurement rounds per case, adaptive batches of at least 25 ms, fixed heap, deterministic
  inputs, exact pre/post verification, and an observed output sink outside timing.
- Acceptance is per case: the median of generated per-fork medians must be no greater than `1.15x`
  the median of the corresponding direct-loop per-fork medians. Report every fork and ratio. Do
  not average failures together, widen the threshold after measurement, or put timing in JUnit.
- If a required case exceeds `1.15x`, retain `In progress` or `Review needed` and investigate the
  generated/JIT code shape. Environmental invalidity may justify rerunning the unchanged protocol;
  it does not justify completion.

## Architecture constraints

- Planning selects CPU ownership only. CPU analysis owns lowering, structural specialization,
  strategy selection, and declarations; CPU finalization owns compatible generation/reuse after
  shared assignment; Runtime only invokes the immutable prepared executable.
- Generated hot code receives direct typed carriers and primitive cold geometry. It must not see
  `Operation`, `CompiledNode`, graph objects, backend discovery, route selection, cache policy, or
  benchmark evidence.
- Prepared recipes remain immutable and reusable. Concurrent runs use distinct `RunState` and
  invocation-private geometry; generated classes retain no mutable run state.
- Preserve universal long entry signatures and all general carrier/layout forms. Dense integer
  code shape is a cold-proved specialization, not a narrowing of the supported domain.
- Stop if parity requires a shared contract, public API, dependency, architecture, semantic,
  resource, or route-selection change.

## Local decisions

- Group affine copy and data movement because both already emit typed generated loops and share the
  dense heap-array integer address correction boundary. No bridge-only family enters this task.
- Require three separate parity cases. Affine copy, repeating movement, and functional replacement
  exercise materially different generated control flow; no passing case masks another failure.
- Reuse `1.15x` from CPU 0007A0 as the local near-parity threshold. It is an actionable per-case
  target with environmental allowance, not a universal speed claim.
- Preserve the direct/general split. The optimization specializes only proved dense heap-array
  structure and does not narrow long-address, segment, mixed-carrier, or arbitrary-layout support.

## Known limitations

- The performance gate covers three representative large dense heap-array cases on the recorded
  local environment. It does not claim parity for every movement mapping, carrier, shape, or CPU.
- General segment/mixed/arbitrary-layout forms receive semantic and bytecode/dispatch validation,
  but no timing threshold in this task.
- This plan records source/bytecode defects but intentionally records no pre-implementation timing
  ratio. The implementation context must measure the reproducible baseline before correction.
