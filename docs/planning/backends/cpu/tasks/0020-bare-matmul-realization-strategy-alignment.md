## Change class

Class C — selected MATMUL loop form, generated specialization, and prepared work domain must

## Goal

Make a bare portable CPU `MATMUL` executable under the default `SCALAR` compute preference even
when its geometry also makes a Vector API realization eligible. Keep explicit
`VECTOR_IF_ELIGIBLE` selection and existing scalar/vector algorithms intact.

## Scope

- Establish a failing regression before the fix for a same-type, contiguous rank-two MATMUL
  such as `FLOAT32 [2,63] × [63,128]`. Source audit currently shows
  `CpuMatmulCandidateSelector.select` chooses `DIRECT_N_VECTOR` from geometry without reading
  the compute preference, while `CpuPartitionPreparer` chooses vector strategy and species only
  under `VECTOR_IF_ELIGIBLE`. This is a source-level inference; record the observed failure stage
  and message rather than assuming it.
- Align the selected `CpuMatmulIr.Realization`, `ExecutionStrategy`, specialization strategy and
  species bits, work count, and generated route before finalization. With `SCALAR`, choose the
  already-eligible direct or 2×2 scalar realization; with `VECTOR_IF_ELIGIBLE`, retain the
  eligible direct-N or 2×2 vector realization and its exact preferred species. Preserve the
  established geometry thresholds and candidate order unless a test proves they are themselves
  inconsistent.
- Cover the four homogeneous Vector API types (`FLOAT32`, `FLOAT64`, `INT32`, `INT64`), small
  scalar work, both direct and tiled eligible shapes, non-unit-stride/terminal ineligibility,
  and the portable public path. Use `INT32` for an exact public Engine regression because the
  optional OpenBLAS peer cannot mask that CPU route.
- Add a cold fail-closed consistency check only if needed to prevent a future mismatch between
  the typed MATMUL realization and generated specialization. Keep it out of per-element work.

## Non-goals

No new MATMUL algorithm, Vector API emitter rewrite, default/preference change, threshold
retuning, performance speedup claim, OpenBLAS selection change, mixed/low-precision capability,
fusion/epilogue redesign, CPU 0018 recognition change, or Model/Prepare/Runtime/Engine production
API change. If the correction needs generated bytecode or a broader owner, stop and replan.

## Acceptance criteria

- A pre-fix focused test demonstrates the mismatch or its concrete failure for a vector-eligible
  bare MATMUL under default `SCALAR`; retain the red evidence in the task result.
- Under `SCALAR`, typed IR realization is scalar, specialization compute is scalar with species
  bits zero, and the work domain matches the chosen direct or tiled scalar form. Preparation,
  finalization, and execution succeed with correct results.
- Under `VECTOR_IF_ELIGIBLE`, the same eligible geometries retain the direct-N or tiled vector
  form, matching vector strategy/preferred species and work domain. Explicit scalar, vector,
  parallel-scalar, and parallel-vector orchestration remains internally consistent where legal.
- For all four homogeneous vector-capable types, eligible direct/tiled and ineligible controls
  keep their supported behavior. The public bare `INT32` graph returns exact matrix-product
  values through `Engine.standard()`; floating regressions use the existing operation/dtype
  test-only numerical oracle. OpenBLAS routes and low/mixed types remain unchanged.
- Emission for a fixed specialization is unchanged. Selecting a different scalar realization
  naturally selects its existing distinct artifact identity and bytes, without changing the
  generator schema. If the emitter itself must change, stop and replan with generated-versus-
  optimal-direct Java shape and performance evidence rather than silently broadening this task.
