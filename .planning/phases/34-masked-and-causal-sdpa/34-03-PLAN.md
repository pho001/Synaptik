# Plan 34-03: Causal SDPA Support And Rejection Detail

**Phase:** 34 Masked And Causal SDPA
**Requirements:** METALSDPAMASK-01, METALSDPAMASK-02
**Status:** Planned
**Wave:** 3

## Objective

Add causal SDPA support for the public `AttentionOptions.causal()` path and preserve exact rejection details for causal variants outside the supported Metal scope.

## Tasks

1. Decide and implement the causal representation:
   - consume the existing expanded causal/effective BOOL mask when it is device-resident, or
   - generate a causal mask/bias inside the Metal-lowered SDPA path.
2. Ensure external mask plus causal mask semantics match the public logical-AND contract.
3. Add planner diagnostics distinguishing:
   - causal-only supported,
   - external+causal supported,
   - causal shape/rank unsupported,
   - causal mask materialization unsupported,
   - fully unsupported backend native causal path.
4. Add parity tests for causal-only and external+causal rank-3/rank-4 attention.
5. Add negative tests for unsupported dtype/layout/rank cases and CUDA capability-gated causal rejection.

## Acceptance Criteria

- Supported causal direct SDPA stays Metal-owned and matches CPU public attention behavior.
- External+causal masks produce the same output as public CPU logical-AND semantics.
- Rejection messages let coverage reports distinguish causal blockers from generic mask blockers.
- No public API changes are required.

## Threat Model

- **Threat:** Causal masks are generated as CPU leaves and force a boundary in hot paths.
  **Mitigation:** Tests assert device-resident mask handling or backend-internal causal generation evidence.
- **Threat:** Off-by-one causal convention.
  **Mitigation:** Use fixtures that prove `j == i` is allowed and `j > i` is blocked.
