# Plan 37-01: Dense Loss Lowering Contract

**Phase:** 37 Loss-Adjacent Metal Lowering
**Requirements:** METALLOSS-01, METALLOSS-03
**Status:** Planned
**Wave:** 1

## Objective

Lock the exact dense loss-adjacent Metal contract before native support is claimed.

## Tasks

1. Trace dense `NLL_LOSS` and dense `CROSS_ENTROPY_LOSS` graph construction, CPU kernels, output shape, dtype, class-dimension, and reduction semantics.
2. Add a Metal loss semantics helper or extend `MetalPartitionSupport` with stable dense-loss reason codes:
   - supported candidate scope,
   - unsupported dtype,
   - unsupported layout,
   - unsupported rank/axis/shape,
   - unsupported reduction/target semantics.
3. Update `GpuLoweringCoverageMatrix` / `GpuTargetSemanticsContract` if the current loss rows do not distinguish dense loss from index-target loss clearly enough.
4. Add planner tests proving dense loss rows are either admitted only inside the locked scope or rejected with stable details.
5. Document the dense loss contract in `docs/gpu-lowering-coverage.md` and `docs/metal-backend.md`.

## Acceptance Criteria

- Dense loss support scope is explicit before execution work begins.
- Index-target loss rows remain separate and are not accidentally promoted.
- Planner diagnostics identify why dense loss variants are unsupported.

## Threat Model

- **Threat:** Dense loss support is claimed through an approximate formula.
  **Mitigation:** Contract tests must compare CPU formulas, output shape, and class-axis behavior before support rows change.
