# Plan 38-02: Backward Native Or Stable-Rejection Execution

**Phase:** 38 Metal Training Backward Coverage
**Requirements:** METALTRAIN-01, METALTRAIN-02
**Status:** Planned
**Wave:** 2

## Objective

Verify or implement Metal execution for scoped supported backward-adjacent operations, while keeping unsupported backward families as explicit CPU boundaries.

## Tasks

1. Audit `AcceleratorSubgraphLowerer` and Metal native DAG support for the positive backward rows from 38-01.
2. Add missing lowered DAG node mappings or native descriptor handling for supported backward rows where the matrix already says supported but execution evidence is incomplete.
3. Add prepared-execution tests that select Metal for supported backward nodes in `FORWARD_BACKWARD` graphs.
4. Add native parity tests where the Apple shim can execute the backward DAG:
   - softmax/log-softmax gradients
   - min/max reduction gradients
   - scoped SDPA backward if current native ABI exposes enough semantics
5. Keep conv/pool backward, index gradients, scatter, and index-target loss gradients CPU-owned with stable rejection detail.

## Acceptance Criteria

- Supported backward rows have real prepared-execution or native trace evidence.
- Unsupported backward rows remain visible and do not silently shorten adjacent supported Metal regions without a reason.
- CPU gradients remain the parity oracle.

## Verification

```bash
./gradlew test --tests PreparedExecutionBuildTest --tests SoftmaxExecutionTest --tests LogSoftmaxExecutionTest --tests MinMaxReductionExecutionTest --tests AttentionExecutionTest
./gradlew metalTest
git diff --check
```

## Threat Model

- **Threat:** A backward op appears selected for Metal but executes through tensor-array or CPU fallback.
  **Mitigation:** Tests must inspect trace/backend path evidence, not just numerical parity.
