  <action>
    Extend `CudaAcceleratorBufferBinder` with a resolver similar to Metal:
    - Add `public AcceleratorBufferBindings<CudaBufferBinding> resolve(AcceleratorBufferRequest request, ResolvedAcceleratorInputs inputs, AcceleratorBufferDecision decision, ExecutionContext context, CudaBufferAllocator allocator)`.
    - When `decision.path() != BUFFER_BINDING`, return empty bindings.
    - Register `new CudaDeviceToCpuMaterializer(allocator)` using `context.registerDeviceToCpuMaterializer(ComputeBackend.GPU_CUDA.name(), ...)`.
    - For each external input: if `context.deviceBufferBindingForNodeId(nodeId)` is a compatible readable `CudaBufferBinding`, reuse it. Otherwise require CPU current storage and create an input binding with `allocator.createInputBinding(nodeId, tensor)`, register `new CudaBufferResource(allocator, created.handle())`, and attach non-prepared inputs as `StorageResidency.DEVICE_OWNED` or `HOST_SHARED_DEVICE_BUFFER` only if the implementation has actually uploaded the bytes. For CUDA uploads use `HOST_SHARED_DEVICE_BUFFER` for input bindings whose CPU array remains current after upload.
    - For each output: if `context.writableDeviceBufferBindingForNodeId(nodeId)` is a compatible writable CUDA binding, reuse it. Otherwise allocate `allocator.createOutputBinding(nodeId, layout)`, register `CudaBufferResource`, reserve it with `context.reserveDeviceBufferBinding(nodeId, created)`, and return it in output bindings.
    - Compatibility requires backend `GPU_CUDA`, `CudaBufferBinding`, same dtype, same shape, same strides, same storage offset, same logical element count, available handle, and required access READ or READ_WRITE for inputs / WRITE or READ_WRITE for outputs.

    Update `PreparedCudaExecutable.execute(...)`:
    - Keep bridge/context/executable readiness checks.
    - Build `ResolvedAcceleratorInputs` using `AcceleratorPreparedInputResolver.resolve(...)`.
    - Build an `AcceleratorBufferRequest` from `dagSpec`, bridge executable ids/dtypes, and runtime layouts.
    - Call `bufferBinder.decide(...)` and publish `lastAcceleratorBufferDecision`.
    - If path is `BUFFER_BINDING`, create allocator with `bridge.createBufferAllocator(bridgeContext)`, resolve bindings, call `bridge.executeBuffers(bridgeContext, bridgeExecutable, bindings.inputs(), bindings.outputs())`, then attach output bindings as readable `StorageResidency.DEVICE_OWNED` with reason `cuda buffer binding output`.
    - If buffer execution throws, publish a new decision with path `UNAVAILABLE` in REQUIRE mode or `CPU_FALLBACK` otherwise, reason code `NATIVE_BUFFER_EXECUTION_FAILED`, and reason prefix `CUDA buffer binding execution failed:`.
    - In REQUIRE mode, throw using the existing message shape before tensor-array or CPU fallback.
    - In AUTO/default mode, fallback visibly using existing CPU fallback steps if buffer execution is unavailable or fails.
