# Plan 33-03: Prepared Execution And Region Legality Integration

**Phase:** 33 GPU Layout Router And Strided Materialization
**Requirements:** METALLAYOUT-02
**Status:** Planned
**Wave:** 3

## Objective

Integrate layout router decisions into Metal prepared execution and operation legality so router-produced dense bindings can feed supported consumers without hidden CPU materialization.

## Tasks

1. Thread router decisions through `DeviceLayoutViewPropagator`, `ExecutionContext`, and prepared-step metadata so each layout repair records route kind, reason code, bytes, and target node id.
2. Update Metal prepared execution REQUIRE-mode behavior so missing layout materialization fails before tensor-array or CPU fallback when buffer execution is required.
3. Update `MetalPartitionSupport` and lowering legality where needed so non-dense source chains can be accepted when a legal router repair precedes a dense-only consumer.
4. Prove key chains stay device-owned:
   - `linear/matmul -> reshape -> permute -> contiguous -> logSoftmax/reduction`
   - `expand/broadcast -> contiguous -> elementwise/where` when broadcast repair is admitted
   - index-forward consumers remain dense-index safe after layout repair
5. Keep CPU fallback paths trace-visible when router repair is unavailable or rejected.

## Acceptance Criteria

- Legal router-produced dense bindings are consumed by later Metal operations without `CPU_CONSUMER` materialization.
- Missing router support in REQUIRE mode throws a layout-specific failure.
- Existing public tensor outputs are still CPU-readable only at true output/public access boundaries.
- CPU execution and tensor-array fallback behavior remain correct when buffer binding is OFF/AUTO.

## Threat Model

- **Threat:** A repaired dense binding is marked current while the Java tensor shape/layout no longer matches it.
  **Mitigation:** Validate target `AcceleratorBufferLayout` at attach time and assert trace layout metadata.
- **Threat:** CPU materialization disappears from traces instead of being eliminated.
  **Mitigation:** Add negative tests with unsupported layouts that must still report fallback/materialization detail.
