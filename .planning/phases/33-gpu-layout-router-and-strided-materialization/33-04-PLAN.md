# Plan 33-04: Coverage Gates And Docs

**Phase:** 33 GPU Layout Router And Strided Materialization
**Requirements:** METALLAYOUT-01, METALLAYOUT-02, METALLAYOUT-03
**Status:** Planned
**Wave:** 4

## Objective

Close Phase 33 with benchmark coverage targets, regression gates, docs, and verification evidence proving layout repair no longer causes hidden CPU exits on supported Metal paths.

## Tasks

1. Add or promote representative non-contiguous/view workloads under the `METALLAYOUT` requirement family.
2. Add coverage expectations requiring:
   - native Metal buffer execution for supported layout targets,
   - GPU layout materialization evidence,
   - zero tensor-array fallback,
   - zero CPU fallback,
   - zero unexpected `CPU_CONSUMER` materialization inside the hot path.
3. Keep unsupported broadcast/strided/dtype cases visible as expected blocker reasons until implemented.
4. Update `docs/metal-backend.md`, `docs/gpu-lowering-coverage.md`, and troubleshooting docs with the layout router contract, supported routes, non-goals, and REQUIRE-mode behavior.
5. Write `33-VERIFICATION.md` mapping `METALLAYOUT-01/02/03` to code, tests, traces, reports, docs, and residual limitations.
6. Verify local profile artifacts remain unstaged.

## Acceptance Criteria

- Phase 33 coverage gates fail hidden CPU materialization caused by layout repair.
- Reports distinguish metadata-only view, GPU dense materialization, broadcast materialization, direct strided compute, and unsupported layout repair.
- Docs do not claim universal strided compute or CUDA parity.
- Phase 33 requirements have traceable verification evidence.

## Threat Model

- **Threat:** Benchmark gates pass on tensor-array copy execution.
  **Mitigation:** Require buffer-binding backend path and zero tensor-array fallback for supported Metal layout targets.
- **Threat:** Local benchmark/profile output is committed accidentally.
  **Mitigation:** Stage only source/docs/planning files and check `profiles/platform` status before commit.
