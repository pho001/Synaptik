<objective>
Add backend-neutral dtype residency decisions for Metal/CUDA capability diagnostics without expanding native dtype compute beyond proven support.
</objective>

<source_audit>
GOAL: Makes non-floating dtype residency explicit at backend boundaries.
REQ GPUSTORAGE-01: Covered by metadata tests and representable residency decisions for BFLOAT16, INT32, and BOOL.
REQ GPUSTORAGE-02: Covered by stable role-specific Metal/CUDA rejection details.
CONTEXT D-04, D-05, D-06, D-07, D-08, D-12, and D-13 are implemented in this wave.
</source_audit>

<threat_model>
T-16-02: Dtype residency diagnostics could be mistaken for native arithmetic support. Mitigation: separate `residentRepresentable`, `nativeInputLegal`, `nativeOutputLegal`, and `nativeComputeLegal` fields.
T-16-03: Unsupported dtype cases could silently fall back to CPU. Mitigation: every rejected decision carries `GpuLoweringUnsupportedReason.UNSUPPORTED_DTYPE` and exact backend/role/dtype detail.
</threat_model>

    - `GPU_METAL`: `FLOAT32` is legal for input/output/compute; `BOOL` is legal only for external input; `BFLOAT16` and `INT32` are representable metadata but not native input/output/compute.
    - `GPU_CUDA`: `FLOAT32` is legal for native dense buffer input/output/compute; `BFLOAT16`, `INT32`, and `BOOL` are representable metadata but rejected for native buffer execution unless an existing CUDA code path already proves support.
    - `CPU`: all five project dtypes are resident-representable; native GPU legality fields are false.

    Rejected Metal/CUDA decisions must use `GpuLoweringUnsupportedReason.UNSUPPORTED_DTYPE` and detail strings containing `backend=GPU_METAL` or `backend=GPU_CUDA`, `role=...`, and `dtype=...`.
