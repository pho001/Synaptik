# Plan 39-03: Output Buffer And Native Copy Closure

**Phase:** 39 Metal Backend Router And Zero-Copy Closure
**Requirements:** METALROUTER-02, METALROUTER-03
**Status:** Planned
**Wave:** 3
**Depends on:** 39-01

## Objective

Close the remaining Metal native-copy ambiguity by either proving true output-buffer writes for supported MPSGraph executions or making the conservative result-copy path first-class coverage evidence.

## Tasks

1. Add a native copy classification enum, for example:
   - `MPSGRAPH_RESULT_COPY`
   - `TRUE_OUTPUT_BUFFER_WRITE`
   - `UNKNOWN_OR_UNPROVEN`
2. Extend `MetalMpsBridgeExecutionStats` and Metal step attributes with:
   - `metalNativeCopyStrategy`
   - `metalNativeDeviceCopyNs`
   - `metalOutputBufferWriteProven`
3. Add native shim support or Java-side native tests that seed output buffers, execute representative MPSGraph regions, and verify whether returned result storage writes or aliases caller-provided buffers.
4. If true output-buffer write cannot be proven safely, keep the existing copy but require reports to classify it as `MPSGRAPH_RESULT_COPY`.
5. Add coverage/report gates that can fail unexpected native-copy regressions on hot paths without confusing native-device copy with Java array copy-back.

## Acceptance Criteria

- `MetalMpsBridgeExecutionStats` exposes a stable native copy strategy field.
- Text and JSON benchmark reports include the native copy strategy and native-device copy duration.
- Native Metal tests either prove `TRUE_OUTPUT_BUFFER_WRITE` for scoped operations or assert `MPSGRAPH_RESULT_COPY` remains explicit.
- Existing buffer binding tests still require `metalNativeToJavaCopyNs=0` for device-owned buffer path.

## Threat Model

- **Threat:** The project claims zero-copy while MPSGraph still returns separate result storage.
  **Mitigation:** Only mark `TRUE_OUTPUT_BUFFER_WRITE` after sentinel/alias proof; otherwise keep `MPSGRAPH_RESULT_COPY` visible and gate it explicitly.
