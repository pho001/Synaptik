# Plan 32-01: INT32 ABI Residency And Planner Legality

**Phase:** 32 INT32 Index Tensor And Gather Take Path
**Requirements:** METALINTIDX-01
**Status:** Planned
**Wave:** 1

## Objective

Make Metal able to carry `INT32` index tensors through native buffer binding as role-specific external inputs, without claiming generic INT32 compute or output support.

## Tasks

1. Extend Metal dtype capability truth with an index-input role decision for `GATHER` and `TAKE_ALONG_AXIS`.
2. Keep generic `INT32` compute/output rejected with stable `UNSUPPORTED_DTYPE` diagnostics.
3. Update `AcceleratorDTypeResidencyPolicy` or lowering evidence so legal index inputs report `dtype=INT32` residency as index-input evidence, not arithmetic compute evidence.
4. Update Metal buffer allocator/binder/bridge validation to accept `INT32` external input buffers when the lowered executable descriptor expects an index role.
5. Add planner tests proving:
   - legal dense `INT32` index inputs can feed candidate index ops,
   - `INT32` compute/output remains unsupported,
   - CUDA remains unsupported/capability-gated.

## Acceptance Criteria

- `INT32` index tensors can be represented as Metal external input bindings for legal index consumers.
- Generic `INT32` Metal compute/output still rejects visibly.
- Trace or manifest evidence can distinguish `role=indexInput dtype=INT32` from native INT32 arithmetic.
- Existing BF16/BOOL/FLOAT32 Metal dtype tests remain stable.

## Threat Model

- **Threat:** INT32 residency is interpreted as generic INT32 compute.
  **Mitigation:** Role-specific capability methods and tests keep compute/output rejection separate.
- **Threat:** Older native shim silently accepts an incompatible dtype descriptor.
  **Mitigation:** Continue using dtype ABI v3 capability/version checks before widened dtype execution is claimed.
