# Requirements: Synaptik v1.4 Native GPU Operation Coverage Closure

**Defined:** 2026-05-01
**Core Value:** Synaptik must produce correct tensor results through a clean compiled graph architecture while letting the optimizer and tuning system choose high-performance CPU or accelerator execution without hidden regressions.

## v1.4 Requirements

Requirements for the v1.4 milestone. Each requirement maps to exactly one roadmap phase.

### Coverage Truth And Semantics Lock

- [x] **GPUNATIVE-01**: Engineers can inspect the current Metal/CUDA lowering matrix and benchmark coverage reports to identify which listed fallback families are still only rejection evidence versus real native execution.
- [x] **GPUNATIVE-02**: Each targeted operation family has a semantics contract covering dtype, rank, layout, shape, reduction axis, keep-dims behavior, broadcast behavior, numerical tolerance, and backend capability gates.
- [x] **GPUNATIVE-03**: Coverage gates distinguish native buffer execution, tensor-array bridge execution, CPU fallback, and candidate shortening for every target workload.

### Forward Reductions

- [x] **GPURED-01**: Metal and CUDA lowering can represent `SUM`, `MEAN`, `REDUCE_MIN`, and `REDUCE_MAX` as accelerator DAG primitives with axis and keep-dims metadata.
- [x] **GPURED-02**: Backend execution implements supported reduction primitives natively or through backend-owned GPU-side primitive lowering without CPU materialization between region-internal producer and consumer steps.
- [x] **GPURED-03**: Focused CPU parity and trace tests prove reduction outputs stay device-owned until a true graph output, CPU consumer, or gradient publication boundary.

### Normalization

- [x] **GPUNORMX-01**: `LAYER_NORM` and `RMS_NORM` lower to GPU-resident reduction-adjacent DAG primitives or explicit supported sub-DAGs under a shared Metal/CUDA contract.
- [x] **GPUNORMX-02**: Normalization lowering preserves epsilon semantics, gamma/beta broadcasting, dtype/layout legality, and CPU parity across representative normalized shapes.
- [x] **GPUNORMX-03**: Normalization hot paths no longer force CPU materialization between supported matmul/elementwise/reduction-adjacent GPU region steps.

### Forward SDPA

- [x] **GPUSDPA-01**: Forward SDPA semantics are verified for scale, rank, mask/no-mask behavior, dtype support, and backward-pass interaction before planner admission.
- [x] **GPUSDPA-02**: Metal and CUDA either execute supported forward SDPA regions through verified backend primitives/lowering or reject them with stable capability-specific reason codes.
- [x] **GPUSDPA-03**: Transformer-style attention coverage gates prove whether SDPA stayed on GPU and fail hidden CPU exits for the supported case.

### Loss-Adjacent And Indexing

- [x] **GPULOSSIDX-01**: Loss-adjacent flows needed by representative workloads have either GPU lowering for supported dtype/index contracts or explicit stable rejection tied to unsupported semantics.
- [x] **GPULOSSIDX-02**: `GATHER`, `SCATTER_ADD`, `TAKE_ALONG_AXIS`, and index-target loss inputs can keep supported INT32/BOOL/FLOAT device residency across GPU regions where backend execution is legal.
- [x] **GPULOSSIDX-03**: Indexing/loss parity tests cover boundary behavior, duplicate index semantics, ignore-index semantics, and materialization visibility.

### Conv Pool And BOOL Compare Outputs

- [x] **GPUCONVBOOL-01**: Conv/pool workloads receive GPU coverage through supported backend primitives/lowering or explicit capability-gated rejection for unsupported layouts and ranks.
- [x] **GPUCONVBOOL-02**: BOOL-producing compare operations can produce device-resident BOOL outputs for supported Metal/CUDA paths and feed `WHERE`/mask consumers without CPU materialization.
- [x] **GPUCONVBOOL-03**: Conv/pool and BOOL compare coverage reports expose selected region length, lowered primitive count, CPU exits, and backend execution path.

### Coverage Regression Closure

- [x] **GPUCLOSE-01**: Representative transformer, normalization, loss/indexing, and conv/pool workloads have hard coverage thresholds for CPU materializations, fallback counts, region length, and backend execution path.
- [x] **GPUCLOSE-02**: Regression gates fail when a supported target family regresses from native/buffer execution to tensor-array bridge or CPU fallback without an explicit capability reason.
- [x] **GPUCLOSE-03**: Final benchmark reports show before/after fallback reduction for v1.4 target families and keep local calibration/profile artifacts out of committed state unless intentionally promoted.

## Future Requirements

Deferred to later milestones.

### Vendor Library Routing

- **GPULIB-01**: Route supported primitives through cuBLAS, cuDNN, MPSGraph, or other backend-native libraries when calibrated cost evidence shows a benefit over custom kernels.
- **GPULIB-02**: Add a backend-native primitive cost model that can choose among custom kernels, vendor library calls, and CPU fallback using platform-specific evidence.

### Extended Coverage

- **GPUEXT-01**: Support broader high-rank, sparse, dynamic-shape, and advanced indexing combinations beyond the v1.4 representative workload set.
- **GPUEXT-02**: Validate canonical real-CUDA hardware performance and correctness evidence in CI or a documented hardware lane.

## Out of Scope

Explicitly excluded from v1.4 to keep the milestone reviewable.

| Feature | Reason |
|---------|--------|
| Public GPU tensor/device API | Public `Tensor` remains logical; residency belongs in compile/prepare/execute runtime state. |
| Universal operation coverage | v1.4 closes the listed high-impact families first and keeps unsupported combinations explicit. |
| Silent fallback or best-effort replay | Hidden CPU exits invalidate the milestone goal; fallback must be traceable and gateable. |
| Backend-specific architecture forks | Metal and CUDA can execute differently, but shared planning/lowering contracts must remain backend-neutral. |
| Full vendor-library router | Library routing is desirable, but v1.4 first closes operation legality and native execution contracts. |
| Committing local benchmark or calibration artifacts | Local profiles under `profiles/platform/...` are not milestone artifacts unless intentionally promoted to fixtures. |
