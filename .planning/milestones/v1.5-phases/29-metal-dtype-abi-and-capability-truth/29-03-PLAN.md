# Plan 29-03: DType Trace, Report, And Coverage Truth

**Phase:** 29 Metal DType ABI And Capability Truth
**Requirements:** METALDTYPE-01, METALDTYPE-03
**Status:** Planned
**Wave:** 3

## Objective

Expose dtype support decisions in planner diagnostics, traces, and coverage reports so users can distinguish residency, conversion, native compute, native output, and fallback.

## Tasks

1. Find Metal dtype rejection/report surfaces in planner legality, coverage summaries, and benchmark report renderers.
2. Route new dtype decision reason codes into visible rejection details where Metal rejects a region because of dtype role or dtype ABI capability.
3. Update report text/JSON fields or existing reason strings so they can state:
   - dtype residency support,
   - native compute dtype support,
   - native output dtype support,
   - external predicate/input role support,
   - dtype ABI v3 availability.
4. Update coverage truth docs/tests to preserve the rule: semantic lowering support is not native dtype compute support.
5. Add regression tests around report rendering or coverage summaries for representative dtype blocker cases.

## Acceptance Criteria

- Reports can explain why BF16/BOOL/INT32/FLOAT64 stayed resident, converted, or fell back.
- Planner diagnostics include stable dtype role and capability reason details.
- No shared coverage row becomes `SUPPORTED` solely because dtype residency exists.
- Existing FLOAT32 supported reports remain stable.

## Must Haves

- METALDTYPE-03: Coverage reports and planner diagnostics expose dtype-specific support and fallback reasons.

## Threat Model

- **Threat:** Reports become noisy without actionable reason codes.
  **Mitigation:** Render concise role/dtype/reason triples.
- **Threat:** Coverage matrix overclaims dtype execution.
  **Mitigation:** Tests assert residency and compute support remain separate.
