# Plan 29-02: Native ABI v3 DType Descriptor And Optional Probes

**Phase:** 29 Metal DType ABI And Capability Truth
**Requirements:** METALDTYPE-01, METALDTYPE-02
**Status:** Planned
**Wave:** 2

## Objective

Add backward-compatible native dtype ABI v3 discovery so older `_f32` dylibs cannot silently claim widened dtype execution.

## Tasks

1. Add a version constant and Java support/status model for Metal dtype ABI v3.
2. Extend `MetalMpsBridgeCapabilities` with dtype ABI v3 support and version fields.
3. Extend `MetalMpsCapabilityCode` with dtype ABI unavailable/version-mismatch codes.
4. Add optional FFM symbol lookup in `MetalMpsFfmBridge` for:
   - `synaptik_apple_mps_dtype_abi_version`;
   - `synaptik_apple_mps_validate_dtype_abi_v3`.
5. Add native stub symbols that conservatively validate the current dtype contract.
6. Keep existing `_f32` compile/execute functions as the execution path until later phases add widened symbols or router paths.
7. Add tests that prove missing dtype ABI v3 symbols produce unsupported widened-dtype decisions without breaking existing FLOAT32 availability.

## Acceptance Criteria

- Bridge capabilities expose dtype ABI v3 availability independently from layout ABI v2.
- Missing or mismatched dtype ABI v3 is a visible capability state.
- Existing FLOAT32 Metal execution remains eligible when the bridge is otherwise available.
- BF16/BOOL-output/INT32/FLOAT64 cannot be admitted through an older `_f32` dylib.

## Must Haves

- METALDTYPE-02: Versioned Metal native ABI can carry dtype metadata beyond `_f32` without silent support claims.
- METALDTYPE-01: Native capability probing is part of dtype legality.

## Threat Model

- **Threat:** A dylib built before dtype ABI v3 is treated as dtype-capable.
  **Mitigation:** Optional symbol and version checks default widened dtype support to unavailable.
- **Threat:** Dtype ABI gating disables working FLOAT32 paths.
  **Mitigation:** Treat dtype ABI v3 as a widened-dtype capability, not a base bridge requirement.
