# Plan 30-03: BF16 Parity, Tolerance, And Coverage Gates

**Phase:** 30 BF16 Metal Compute And Output
**Requirements:** METALBF16-01, METALBF16-02, METALBF16-03
**Status:** Planned
**Wave:** 3

## Objective

Lock BF16 numeric tolerance and add coverage evidence that supported BF16 hot paths reduce CPU exits without regressing FLOAT32.

## Tasks

1. Define BF16 tolerance policy for Metal-vs-CPU parity:
   - exact raw storage checks for upload/readback,
   - numeric tolerance for matmul/linear and reductions,
   - separate tolerance for normalization and softmax/log-softmax.
2. Add representative BF16 benchmark/coverage targets for MLP and normalization-like paths.
3. Update coverage reports to show BF16 native execution evidence, fallback reasons, dtype role decisions, and CPU materialization counts.
4. Add regression gates that fail if supported BF16 targets unexpectedly fall back to CPU or tensor-array paths.
5. Run focused FLOAT32 Metal gates in the same verification set to guard existing hot paths.

## Acceptance Criteria

- BF16 parity tests document tolerances and pass for admitted families.
- BF16 target coverage reports show fewer CPU exits for supported paths.
- Hidden CPU materialization or tensor-array fallback fails supported BF16 gates.
- Existing FLOAT32 target gates remain green.

## Must Haves

- METALBF16-02: BF16 tolerance and report evidence preserve CPU parity.
- METALBF16-03: BF16 hot-path coverage shows reduced CPU exits without FLOAT32 regression.

## Threat Model

- **Threat:** BF16 is faster only because parity checks are too loose.
  **Mitigation:** Store tolerance policy in tests and docs with raw storage checks where applicable.
- **Threat:** Coverage gates pass despite hidden fallback.
  **Mitigation:** Require native path evidence and forbid unexpected CPU exits for supported BF16 targets.
