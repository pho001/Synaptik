# Plan 30-02: BF16 Primitive Lowering And Native Execution

**Phase:** 30 BF16 Metal Compute And Output
**Requirements:** METALBF16-01
**Status:** Planned
**Wave:** 2

## Objective

Admit scoped BF16 Metal compute/output for high-value existing operation families after the transport path is safe.

## Tasks

1. Update `MetalMpsCapabilities` so BF16 compute/output support is scoped to implemented operation families and native ABI/runtime capability.
2. Update `MetalPartitionSupport` dtype legality for BF16:
   - matmul/linear,
   - elementwise arithmetic/activation chains,
   - softmax/log-softmax if native parity is proven,
   - reductions,
   - LayerNorm/RMSNorm.
3. Update the native shim to build BF16 MPSGraph placeholders, scalar constants, and output tensor data for admitted operations.
4. Keep unsupported BF16 operations rejected with stable `UNSUPPORTED_DTYPE` or `CAPABILITY_MISSING` details.
5. Add CPU parity tests for representative BF16 matmul/linear/elementwise chains.
6. Add native Metal parity tests for admitted BF16 ops, capability-skipped when runtime support is absent.

## Acceptance Criteria

- BF16 matmul/linear and selected elementwise paths execute through Metal when native BF16 support is available.
- Unsupported BF16 families do not shorten regions silently; they reject visibly.
- FLOAT32 Metal admission and execution behavior remains stable.

## Verification

./gradlew test --tests backend.metal.lowering.MetalRegionLowererTest --tests PreparedExecutionBuildTest --tests backend.metal.bridge.MetalMpsFfmBridgeTest

## Must Haves

- METALBF16-01: Legal BF16 Metal regions execute supported high-value flows or reject with stable operation-specific reasons.

## Threat Model

- **Threat:** Planner admits BF16 where MPSGraph lacks semantic parity.
  **Mitigation:** Admit by family and add parity tests before support claims.
- **Threat:** Scalar constants promote BF16 graphs to FLOAT32 without report evidence.
  **Mitigation:** Native shim must use dtype-aware constants or reject the op.
