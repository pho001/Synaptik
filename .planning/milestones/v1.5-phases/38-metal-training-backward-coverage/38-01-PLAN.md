# Plan 38-01: Backward Coverage Matrix And Legality Update

**Phase:** 38 Metal Training Backward Coverage
**Requirements:** METALTRAIN-01, METALTRAIN-02, METALTRAIN-03
**Status:** Complete
**Wave:** 1

## Objective

Create a training/backward source-of-truth contract that maps every v1.5-supported forward family to either verified Metal backward support, stable rejection, or explicit CPU boundary.

## Tasks

1. Add a training/backward coverage truth layer or extend existing target truth so backward rows are not inferred from forward support.
2. Enumerate positive Metal backward-adjacent candidates:
   - `SOFTMAX_GRAD`
   - `LOG_SOFTMAX_GRAD`
   - `REDUCE_MIN_GRAD`
   - `REDUCE_MAX_GRAD`
   - `MIN_GRAD`
   - `MAX_GRAD`
   - scoped `SCALED_DOT_PRODUCT_ATTENTION_BACKWARD`
3. Enumerate explicit blockers:
   - conv/pool backward rows: `CAPABILITY_MISSING`
   - index gradients and scatter: `UNSUPPORTED_DUPLICATE_INDEX`
   - index-target loss gradient: `UNSUPPORTED_INDEX_SEMANTICS`
   - unsupported BF16/BOOL/INT32/FLOAT64 backward variants: stable dtype or role reasons
4. Update `MetalPartitionSupport` tests so backward-context admission/rejection is operation-specific instead of relying on broad forward-family assumptions.
5. Add docs explaining that training support is per backward operation, not inherited from forward support.

## Acceptance Criteria

- Reports/tests can distinguish forward native support from backward native support.
- Unsupported backward paths have stable reason codes.
- No unsupported backward row is marked native-executable just because the corresponding forward op is supported.

## Threat Model

- **Threat:** Forward coverage accidentally implies backward support.
  **Mitigation:** Backward truth rows must be asserted separately from forward target rows.
