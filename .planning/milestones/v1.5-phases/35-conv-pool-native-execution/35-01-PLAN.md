# Plan 35-01: Conv/Pool Semantic And Capability Contract

**Phase:** 35 Conv Pool Native Execution
**Requirements:** METALCONVPOOL-01, METALCONVPOOL-02
**Status:** Completed
**Wave:** 1

## Objective

Define precise Metal conv/pool legality and rejection diagnostics before native execution is enabled. This wave may keep conv/pool unsupported, but it must replace generic `CAPABILITY_MISSING` with scoped, testable reason details where the planner can inspect semantics.

## Tasks

1. Add Conv2D legality helper covering dtype, rank, dense layout, NCHW/OIHW shape, stride, padding, dilation, groups, optional bias, and output shape.
2. Add Pool2D legality helper covering dtype, rank, dense layout, kernel, stride, padding, output shape, max-pool tie note, and avg `countIncludePad`.
3. Integrate helpers into `MetalPartitionSupport.plannerUnsupportedReason(...)` for `CONV2D`, `CONV2D_GEMM`, `MAX_POOL2D`, and `AVG_POOL2D`.
4. Keep native support disabled until Wave 35-02/35-03, but make the reason say whether a case is semantically legal but capability-missing or semantically rejected.
5. Add planner/lowering tests for legal-but-not-yet-native conv/pool and unsupported dtype/layout/rank/groups/dilation/countIncludePad cases.
6. Ensure CUDA conv/pool behavior remains capability-gated.

## Acceptance Criteria

- Metal planner diagnostics distinguish semantic blockers from missing native capability.
- Backward conv/pool remains explicitly out of supported forward scope.
- Existing conv/pool CPU tests and coverage blocker tests remain stable.
- No supported GPU coverage row is claimed until native execution and parity exist.

## Threat Model

- **Threat:** Planner diagnostics imply support before execution exists.
  **Mitigation:** Use legal-but-capability-missing reasons until native parity is added.
- **Threat:** Direct Conv2D and `CONV2D_GEMM` semantics are conflated.
  **Mitigation:** Keep separate legality branches and do not support GEMM-lowered conv unless that exact representation is implemented.
