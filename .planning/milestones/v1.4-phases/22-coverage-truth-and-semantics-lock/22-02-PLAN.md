# Plan 22-02: Semantics Contracts For Target Families

**Phase:** 22 Coverage Truth And Semantics Lock
**Requirements:** GPUNATIVE-02
**Status:** Complete

## Objective

Define operation-family contracts that later backend implementations must satisfy before planner admission.

## Contract Scope

- Reductions: operation kind, axis, negative-axis normalization if applicable, keep-dims, output shape, dtype, rank, non-contiguous layout behavior, NaN/Inf expectations, tolerance.
- Normalization: normalized axes, epsilon, gamma/beta broadcasting, RMS vs layer variance semantics, dtype, output shape.
- Forward SDPA: scale, rank convention, mask/no-mask behavior, mask dtype, softmax axis, backward interaction, tolerance.
- Loss/indexing: target/index dtype, bounds, duplicate index behavior, ignore-index behavior, reduction mode.
- Conv/pool: layout, stride, padding, dilation, kernel shape, pooling reduction mode, rank.
- BOOL compare outputs: output dtype, storage representation, device residency, feeding `WHERE`/mask consumers.

## Files To Inspect

- `src/main/java/operations/reduction/*.java`

- `src/main/java/operations/linalg/scaledDotProductAttention.java`

- CPU kernels for the same families under `src/main/java/backend/cpu/kernels`
- Existing execution tests for these families under `src/test/java`

## Tasks

1. Add contract records or docs close to the GPU lowering coverage layer for each target family.
2. Tie each contract to stable rejection reason fields so unsupported semantics remain explicit.
3. Add tests for contract extraction on at least one representative op per family.
4. Document which contracts are prerequisite for Phase 23 reductions and which are later-family prerequisites.

## Acceptance Criteria

- Reduction contracts are complete enough for Phase 23 implementation without further semantic questions.
- SDPA contract explicitly blocks planner admission until scale/mask semantics are verified.
- BOOL compare contract distinguishes BOOL input residency from BOOL output execution.
- Unsupported semantics produce stable reason codes rather than generic unsupported messages.
