# Plan 26-02: Device Residency For Index Inputs And Boundaries

**Phase:** 26 Loss-Adjacent And Indexing GPU Coverage
**Requirements:** GPULOSSIDX-02, GPULOSSIDX-03
**Status:** Planned
**Wave:** 2

## Objective

Make INT32/BOOL/FLOAT residency and materialization behavior visible around loss/indexing boundaries without changing the public Tensor API.

## Tasks

1. Add or refine diagnostics that describe index tensors as resident-representable but not legal compute inputs for unsupported index/loss primitives.
2. Add prepared-execution tests that show `INT32` target/index tensors produce visible fallback reasons rather than hidden CPU replay.
3. Add trace/report assertions for loss/indexing materialization boundaries and CPU exits.
4. Ensure supported adjacent GPU regions before a loss/index boundary remain selected when their own semantics are legal.

## Acceptance Criteria

- Prepared execution and trace tests distinguish residency evidence from native compute support.
- `CROSS_ENTROPY_LOSS_INDICES` fallback shows `INT32` index-target reason detail.
- `GATHER` / `TAKE_ALONG_AXIS` / `SCATTER_ADD` fallback shows index-family reason detail.
- Adjacent `LOG_SOFTMAX`, matmul, elementwise, reduction, or normalization regions remain GPU-selectable when legal.

## Verification

```bash
./gradlew test --tests PreparedExecutionBuildTest --tests CompiledGraphTraceTest --tests GpuCoverageSummaryTest
```

## Threat Model

- **Threat:** CPU fallback looks like device residency success.
  **Mitigation:** Report distinct native execution, resident-representable dtype, materialization, and fallback reason evidence.
- **Threat:** Unsupported loss/index node shortens a legal preceding GPU region silently.
  **Mitigation:** Add adjacency selection assertions.
