# Plan 25-04: SDPA Coverage Gate And Documentation Closure

**Phase:** 25 Forward SDPA Semantic Enablement
**Requirements:** GPUSDPA-01, GPUSDPA-02, GPUSDPA-03
**Status:** Planned
**Wave:** 4
**Depends on:** 25-01, 25-02, 25-03

## Objective

Close Phase 25 with trace, benchmark, regression, and documentation evidence showing exactly whether forward SDPA stayed device-owned or exited to CPU for each backend and supported variant.

## Tasks

1. Update `GpuHotPathCoverageTargets` expectations for `transformer_block_hot_path` based on actual Phase 25 backend outcomes:
   - native evidence required for any backend marked supported,
   - explicit expected reason codes for any backend that remains rejected,
   - CPU materialization and fallback thresholds aligned with the selected path.
2. Update `GpuCoverageSummary`, benchmark renderers, and tests so SDPA evidence includes execution path, region length, lowered primitive count, direct vs decomposed SDPA path, fallback/rejection reason, CPU materialization count, and native capability evidence.
3. Add or update transformer attention workload tests for `transformer_block_hot_path`, with optional `transformer_block_hot_path_long_seq` or `transformer_block_hot_path_attention_heavy` evidence if deterministic enough.
4. Add regression gates that fail when a supported SDPA path silently regresses to tensor-array bridge or CPU fallback.
5. Update docs:
   - `docs/gpu-lowering-coverage.md`,
   - `docs/metal-backend.md`,
   - `docs/architecture.md`,
   - `docs/compute-flow.md` if materialization/report fields change.
6. Create Phase 25 validation closure and record profile hygiene: local benchmark/profile artifacts remain unstaged unless intentionally promoted.

## Acceptance Criteria

- Coverage reports show truthful SDPA state for Metal and CUDA.
- Supported SDPA paths have native/buffer evidence and fail hidden CPU exits.
- Unsupported SDPA paths remain visible through stable reason codes and target-linked report rows.
- Docs match matrix/truth/runtime behavior.
- `git status --short profiles/platform` is checked and no local profile artifacts are included as phase evidence.

## Threat Model

- **Threat:** Benchmark reports imply SDPA stayed on GPU when it used tensor-array bridge or CPU fallback.
  **Mitigation:** Report and regression tests require backend path, native evidence, fallback counts, and materialization counts.
- **Threat:** Local benchmark profiles are accidentally treated as canonical phase evidence.
  **Mitigation:** Validation and summary record profile hygiene and keep profile artifacts unstaged.
