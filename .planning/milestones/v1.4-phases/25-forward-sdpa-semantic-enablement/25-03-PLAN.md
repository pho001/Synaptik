# Plan 25-03: CUDA Forward SDPA Support-Or-Rejection Contract

**Phase:** 25 Forward SDPA Semantic Enablement
**Requirements:** GPUSDPA-01, GPUSDPA-02, GPUSDPA-03
**Status:** Planned
**Wave:** 3
**Depends on:** 25-01

## Objective

Make CUDA forward SDPA honest and auditable: either implement a real backend-owned legal path for the supported contract or keep CUDA as explicit stable rejection with no false `SUPPORTED` matrix row.

## Tasks

1. Audit current CUDA lowerer, legality adapter, prepared executable, and native shim for direct SDPA support gaps.
2. Decide the CUDA path based on local code feasibility:
   - direct native/lowered SDPA path for legal FLOAT32 rank 3/4 unmasked cases, or
   - stable `CAPABILITY_MISSING` / `UNSUPPORTED_OPERATION` rejection if native support is not implemented in this phase.
3. If implementing CUDA support:
   - add CUDA DAG/native execution for direct unmasked SDPA or a backend-owned decomposed sub-DAG,
   - validate rank/shape/scale metadata before launch,
   - add Java tests that check prepared execution and stable unsupported mask/dtype/layout cases,
   - keep native CUDA compile/execution capability-gated when `nvcc` is unavailable.
4. If retaining explicit rejection:
   - update coverage matrix/truth and CUDA legality tests so the unsupported state is stable, target-linked, and report-visible,
   - ensure unsupported direct SDPA does not shorten adjacent supported GPU regions without a visible reason.
5. Update docs to avoid implying CUDA direct SDPA support without native evidence.

## Acceptance Criteria

- CUDA forward SDPA matrix status matches reality: supported only if native/lowered execution exists, otherwise explicit fallback/unsupported.
- CUDA legality exposes stable unsupported details for direct SDPA, masks, dtype/layout/rank blockers, and unavailable native capability.
- Portable tests pass without `nvcc`; native CUDA tests are documented as optional hardware/toolchain gates.
- CUDA does not mirror Metal admission unless its own backend evidence exists.

## Must Haves

- GPUSDPA-02: CUDA either executes supported forward SDPA through verified backend primitives/lowering or rejects with stable capability-specific reason codes.
- GPUSDPA-03: CUDA coverage evidence proves whether SDPA stayed on GPU or exited with visible reason.

## Threat Model

- **Threat:** CUDA Java lowering claims support while native execution is absent or uncompiled.
  **Mitigation:** Matrix support requires executable/native evidence; otherwise stable capability rejection remains the expected result.
- **Threat:** Local lack of `nvcc` hides a native compilation failure.
  **Mitigation:** Portable tests assert capability-gated behavior and docs require a CUDA-equipped lane for native claims.
